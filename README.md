# Terraform Provider Hello (PoC)

A minimal Terraform provider that demonstrates the full provider lifecycle —
build, version, sign, publish to a self-hosted registry on GitHub Pages, and
test end-to-end via the [Terraform Provider Registry Protocol][registry].

[registry]: https://developer.hashicorp.com/terraform/internals/provider-registry-protocol

The provider has a single resource, `hello_world`, which takes a `name`
attribute (default `world`) and prints a message on each lifecycle event:

| Lifecycle | Output            |
| --------- | ----------------- |
| Create    | `hello, <name>!`  |
| Update    | `<name> changed!` |
| Delete    | `bye, <name>!`    |

Messages are surfaced as Terraform diagnostics warnings, so they appear in
normal `terraform apply` / `terraform destroy` output without requiring
`TF_LOG`.

## Architecture

This repo (`paul-the-wizord.github.io`) is a GitHub **user-pages** repo, so
its contents are served at the host root `https://paul-the-wizord.github.io/`.
That root is exactly where the Terraform registry protocol's service discovery
document (`.well-known/terraform.json`) must live. The repo therefore holds
both the provider source code and the served registry metadata.

```
paul-the-wizord.github.io (this repo — user pages, served at host root)
├── main.go                              # provider entrypoint
├── internal/provider/                   # provider + resource implementation
├── .github/workflows/
│   ├── 1-build-and-release.yml          # push to main → tag + build + sign + release
│   ├── 2-publish-registry.yml           # after workflow 1 → commit registry JSON to this repo
│   └── 3-test.yml                       # after workflow 2 → terraform apply/change/destroy
├── test/                                # end-to-end terraform test
├── gpg/public-key.asc                   # signing public key (committed)
│
│   ── generated by workflow 2, served by GitHub Pages ──
├── .nojekyll                            # disables Jekyll so .well-known/ is served
├── .well-known/terraform.json           # service discovery: {"providers.v1": "/v1/providers/"}
└── v1/providers/example/hello/          # registry metadata (extensionless, per protocol)
    ├── versions                         # "List Available Versions" response
    └── <version>/download/linux/amd64   # "Find a Provider Package" response
```

Registry metadata files are **extensionless** (`versions`, `amd64`) because the
origin registry protocol requests paths like `.../versions` and
`.../download/linux/amd64` — GitHub Pages serves these as static files when
`.nojekyll` is present.

Provider binaries live as **GitHub Release assets** in this repo; the Pages
site serves only the lightweight registry metadata JSON that points at them.

**Provider address:** `paul-the-wizord.github.io/example/hello`

## One-time bootstrap

See [`docs/setup.md`](docs/setup.md). In short:

1. Rename any prior `paul-the-wizord.github.io` content repo (e.g. to
   `paul-the-wizord-old`) so the host-root slot is free, then create a fresh
   empty repo named `paul-the-wizord.github.io`.
2. Generate a GPG keypair; commit the public key to `gpg/public-key.asc`.
3. Add repo secrets: `GPG_PRIVATE_KEY`, `GPG_PASSPHRASE`.

No `PAGES_PAT` is needed — the publish workflow commits to the same repo
using the default `GITHUB_TOKEN`.

## CI pipeline

| # | Workflow               | Trigger             | What it does                                              |
|---|------------------------|---------------------|-----------------------------------------------------------|
| 1 | `1-build-and-release`  | push to `main`      | bump patch tag, build linux/amd64, GPG-sign, create release |
| 2 | `2-publish-registry`   | `workflow_run` (#1) | regenerate registry metadata, commit to this repo        |
| 3 | `3-test`               | `workflow_run` (#2) | pin latest version, `terraform init/apply/change/destroy` |

Workflows chain via the `workflow_run` trigger (not `release: published`)
because releases created with `GITHUB_TOKEN` don't emit events that trigger
other workflows. Workflow 2's commit message includes `[skip ci]` to avoid
re-triggering workflow 1.

### Why `workflow_run` instead of `release: published`?

GitHub Actions does not fire `release` events for releases created by a
workflow using the default `GITHUB_TOKEN`. The `workflow_run` trigger
sidesteps this: workflow 2 listens for workflow 1's completion, and workflow 3
listens for workflow 2's completion.

## Local development

For fast iteration without publishing, use `dev_overrides` in
`~/.terraformrc`:

```hcl
provider_installation {
  dev_overrides {
    "paul-the-wizord.github.io/example/hello" = "/path/to/terraform-repository-template/bin"
  }
  direct {}
}
```

Then:

```bash
make build VERSION=0.0.1
cd test
terraform apply     # note: init is skipped with dev_overrides
```

## Run the test

After the registry is published (or locally with dev_overrides):

```bash
make test
# or directly:
bash test/run-test.sh
```

The test script:
1. Generates `main.tf` pinning the latest release version (via `PROVIDER_VERSION`
   env var in CI, or `~> 0.0` locally).
2. `terraform init` with retry loop (waits for GitHub Pages propagation).
3. Creates the resource → asserts `hello, world!` in output.
4. Changes `name` to `earth` → applies → asserts `earth changed!`.
5. Destroys → asserts `bye, earth!`.

## Using the provider

Once the registry is live, any Terraform project can use the provider:

```hcl
terraform {
  required_providers {
    hello = {
      source  = "paul-the-wizord.github.io/example/hello"
      version = "~> 0.0"
    }
  }
}

provider "hello" {}

resource "hello_world" "demo" {
  name = "world"
}
```

```bash
terraform init
terraform apply
# Warning: hello, world!
terraform destroy
# Warning: bye, world!
```

Verify the registry is live:

```bash
curl https://paul-the-wizord.github.io/.well-known/terraform.json
# {"providers.v1": "/v1/providers/"}
```


## Key design decisions

- **Single repo:** Provider source and registry metadata live in the same
  user-pages repo. No cross-repo pushes, no PAT needed.
- **Extensionless registry files:** The origin registry protocol requests
  `/versions` and `/download/:os/:arch` (no `.json` extension). GitHub Pages
  serves these as static files when `.nojekyll` disables Jekyll.
- **Patch-bump versioning:** Every push to `main` creates the next patch
  version (`v0.0.1` → `v0.0.2` → ...). No manual versioning.
- **GPG signing:** Provider checksums are signed with a GPG key whose public
  half is committed to the repo. Terraform verifies the signature on install.
- **Diagnostics for output:** Messages are surfaced via
  `resp.Diagnostics.AddWarning()`, which appears in normal Terraform output
  without requiring `TF_LOG`.
